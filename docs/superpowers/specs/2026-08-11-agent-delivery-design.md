# 二期第一阶段设计：Agent 工具结果可交付

## 1. 背景

当前项目已经具备 persona / long-term memory / proactive messaging / humanized send 的一期基础能力，`web_search`、`write_doc`、`gen_image` 也已经存在基本工具入口，但结果交付体验还不统一：

- 有的工具更像“内部能力”，不够像真人在聊天里自然给结果
- 失败时缺少前台自然解释与后台可排查日志的统一约定
- 三种工具没有一套共享的交付标准，后续扩展容易分叉

本阶段只处理你确认的二期第一优先级：先把 Agent 工具做成“结果能直接回到聊天里”的形态，再做主动发送消息，最后再完善控制台。

## 2. 目标

本阶段同时处理三种工具：

- `web_search`
- `write_doc`
- `gen_image`

本阶段的核心目标：

1. 工具结果能直接回到聊天里
2. 结果表达要像角色本人在微信里正常说话
3. 优先发送结果本体，再补一句自然说明
4. 失败时前台自然解释，后台保留具体错误日志
5. 三种工具共享统一交付约定，避免各自实现一套发送逻辑

## 3. 非目标

本阶段明确不做：

- 搜索来源卡片、来源列表、报告式摘要
- `docx` / `pdf` 多格式导出
- 富交互卡片、后台错误展示页面
- 新的异步 outbox / job 投递体系
- 控制台大改
- 复杂自动重试编排
- 主动发送消息策略升级

## 4. 用户体验原则

### 4.1 结果要像真人回消息

工具不是“系统能力播报”，而是角色本人在当前语境下临时查了一下、整理了一下或做了一下，然后把结果回给对方。

所有结果都必须遵守：

- 语气结合角色性格
- 语气结合当前上下文
- 表达尽量像微信聊天
- 不出现客服腔、系统播报腔、论文摘要腔

### 4.2 默认呈现方式

统一默认规则：

- `web_search`：直接回一句像真人的话
- `write_doc`：先发 `Markdown` 文件，再补一句自然说明
- `gen_image`：先发图片，再补一句自然说明

自然说明要短，不额外拉长对话，也不抢结果本体的主位。

### 4.3 失败时的体验

前台：

- 不直接暴露 HTTP 错误、provider 名、栈信息、内部工具名
- 用自然且角色化的方式解释失败
- 是否说成“我这边浏览器刚刚有点问题”“网页没刷出来”“刚刚那个地方有点卡”等，由模型自己判断

后台：

- 保留具体错误日志，方便排查

## 5. 三种工具的交付语义

### 5.1 `web_search`

目标不是展示搜索过程，而是像角色本人临时用手机查了一下，再自然回答。

行为要求：

- 默认只给结论
- 默认不列来源
- 默认不做长摘要
- 是否先发一句“等下我看一下”“我查查”之类，由模型根据当前语境和角色性格自己判断
- 如果失败，模型可自由选择更生活化的自然解释，不做硬编码模板

示例风格：

- “等下，我看一眼。”
- “我刚查了下，这个大概就是……”
- “我看了一下，应该是……”

### 5.2 `write_doc`

第一阶段只支持 `Markdown`。

行为要求：

- 工具产出真正可发送的 `.md` 文件
- 聊天里优先直接发送文件
- 文件发送后，再补一句自然说明
- 自然说明更像“我给你整理好了”“你直接看这个就行”这种微信语气

### 5.3 `gen_image`

目标是直接回图，而不是先给链接。

行为要求：

- 用户明确指定生成数量时按用户需求
- 用户未指定时由模型自行判断
- 实现层加安全上限，避免一次生成过多图片
- 聊天里优先直接发图片
- 发图后补一句自然说明
- 如果失败，由模型按语境和角色自由生成自然解释

## 6. 统一交付约定

### 6.1 核心思路

三种工具都产出统一的“交付结果”，再由聊天发送层统一发送，而不是每个工具自己实现整套发消息逻辑。

不新增第二套消息系统，继续复用现有主链路：

`sink.AI -> persona tool -> sink 发送`

### 6.2 数据结构约定

在现有 `ToolCallResult` 基础上，统一抽象出以下语义：

- `Content`
  - 供模型继续组织语言
  - 或直接作为用户可见的自然说明 / 结论文本
- `Files`
  - 供 `write_doc` 返回可发送文件
- `Images`
  - 供 `gen_image` 返回图片
- `Async`
  - 保留现有异步能力语义
- 失败元信息
  - 用于日志，不直接透给用户

### 6.3 发送顺序

发送层按统一规则决定如何交付：

1. 只有文本：直接发文本
2. 有文件：先发文件，再发一句自然说明
3. 有图片：先发图片，再发一句自然说明

如果同时有多种结果，发送顺序优先结果本体，再说明，避免说明抢在结果前面。

## 7. 模型行为约束

### 7.1 搜索前的过渡语

搜索前是否先发过渡语，不做硬规则：

- 由模型根据语境决定
- 由角色设定决定
- 由对话节奏决定

例如：

- 有些角色会直接说“等下，我看一下”
- 有些角色会省略过渡，直接在最终消息里说“我刚查了下……”

### 7.2 失败解释

失败解释也不做固定模板，而是给模型一个边界：

- 必须自然
- 必须像角色本人
- 不能暴露底层技术报错
- 可以使用生活化解释，如“浏览器有点抽”“网页没打开”“刚刚那个页面没刷出来”等

## 8. 日志设计

第一阶段先不做后台可视页面，只写日志 / trace。

每次工具调用至少记录：

- `tool_name`
- `bot_id`
- `sender`
- `delivery_kind`
  - `text`
  - `file`
  - `image`
- `result_count`
- `success`
- `error_stage`
  - 例如 `search`
  - `generate`
  - `upload`
  - `send`
- `error_message`
- `explained_to_user`
  - 是否已做自然解释

日志只保留必要摘要，不整段记录敏感隐私内容。

## 9. 代码落点

### 9.1 发送主链路

主要改造点：

- `internal/sink/ai.go`

职责：

- 统一处理三种工具的交付顺序
- 统一发送文件 / 图片 / 文本
- 统一失败兜底与日志记录

### 9.2 persona 工具

主要改造点：

- `internal/persona/search.go`
- `internal/persona/doc.go`
- `internal/persona/image.go`
- `internal/persona/persona.go`
- `internal/persona/tools.go`

职责：

- 各工具只负责产出标准化结果
- 不在工具内部散落复杂发送行为
- 统一返回给发送层处理

### 9.3 ToolCallResult 与消息组织

关联点：

- `internal/ai/chat.go`

职责：

- 保持现有工具返回结构可被主链路消费
- 允许工具结果进入一轮轻量后处理
- 但第一阶段不扩展成长报告式二次生成

## 10. 验收标准

满足以下条件即可视为本阶段完成：

1. 用户让角色“查一下”时，结果能像真人一样直接回到聊天里
2. 用户让角色“写个文档”时，能直接收到一个 `.md` 文件和一句自然说明
3. 用户让角色“画一张图”时，能直接收到图片和一句自然说明
4. 三种工具的交付体验一致，不割裂
5. 失败时用户看到的是自然解释，而不是技术报错
6. 后台日志能定位具体是哪一个工具、哪一步失败

## 11. 风险与缓解

### 风险 1：模型输出仍然过于“工具腔”

缓解：

- 在 system 约束中明确强调角色化、微信化表达
- 对 `web_search` 结果约束为“只给结论，不列来源”

### 风险 2：不同工具交付逻辑再次分叉

缓解：

- 所有交付都走统一发送层
- 工具内部不直接拼装复杂外发逻辑

### 风险 3：失败话术太假或太模板化

缓解：

- 不写死单一模板
- 只给模型边界和风格约束
- 允许按角色和语境自由发挥

### 风险 4：图片数量失控

缓解：

- 用户明确指定时按需求
- 未指定时模型可判断
- 发送层或工具层增加硬上限

## 12. 后续阶段衔接

本阶段完成后，按既定优先级进入下一阶段：

1. 主动发送消息能力升级
2. 控制台完善

本设计文档只覆盖第一阶段，不预支后两阶段的实现细节。
